ZEN API / live pixels / Python

Stream a frame.
Process it before display.

Receive pixels while ZEN acquires. Decode them into a NumPy array, optionally process that array, and update the live view.

Add processing where the frame is already an array.

Models need setup; simple thresholds do not.

Semantic segmentation and denoising require the matching CZANN model and inference dependencies. The example creates one reusable ONNX inferencer before receiving frames; semantic tiled inference is not implemented here.

Receive and display run at different rates.

Async reception does not make processing parallel.

The example uses one qasync/Qt event loop, and processing runs synchronously inside async for. Slow processing can delay both reception and GUI updates. The single display slot prevents a GUI-frame backlog; it is not a processing-worker queue. Consider workers and an explicit buffering policy for heavier algorithms.

Pixels arrive with acquisition context.

Subscribe, decode, inspect

UI startup uses monitor_all_experiments(). API startup first starts an experiment and then uses monitor_experiment() with its ID.

The payload carries frame position, size, scaling, and stage position. Set the NumPy pixel type to match the acquisition. With enable_raw_data=True, payloads can be partial rectangles or scan lines rather than complete frames.

What this example does not add

The script does not wait for a finished CZI before processing. ZEN owns acquisition and recording; the Python code shown here does not export processed frames to a new CZI.

Online analysis is not automatically feedback control. This example does not send processing-driven stage or experiment changes back to ZEN.

Closing the window cancels the stream task, stops the display timer, and closes the streaming channel. This is not a command to stop ZEN acquisition.
